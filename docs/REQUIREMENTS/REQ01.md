# REQ01 — 피드백 기반 품질·비용 측정

[완료 기준](../GOAL/REQ01/README.md)

현재 평가 대상 과제는 REST Countries FE-01이다. 아래 FE-02 기록은 종료한 FAQ 제한 검증의 역사적 증거이며 현재 과제 범위를 뜻하지 않는다.

## 문제와 목적

첫 결과의 품질과 토큰만 비교하면, 목표 품질에 도달하기까지 필요한 수정 비용을 알 수 없다. 비교군마다 동일한 초기 과제에서 출발해 최초 시도와 피드백 수정의 품질·토큰 변화를 모두 기록하고, 비슷한 완성도에 도달한 시점의 누적 비용을 비교한다.

## 확정 요구사항

- `--repeats`는 초기 파일을 다시 배치하는 독립 반복이다. 한 반복 안에서 최초 시도 1회와 평가 피드백을 받은 수정 최대 2회를 수행한다. 수정은 기존 결과물과 Codex 세션을 이어받는다.
- 각 시도 직후 같은 기준으로 평가하고, 실패 항목과 근거를 다음 수정 지시로 전달한다. 이미 통과한 기능을 유지하도록 지시한다.
- 각 시도의 점수, 직전 시도 대비 점수 변화, 평가 범위와 미평가 사유를 보존한다. 최초 점수와 목표 품질에 처음 도달한 시도 번호를 구분한다.
- 입력·출력·캐시 입력 토큰과 실행 시간을 **시도별 증분 및 누적값**으로 기록한다. 예를 들어 총 토큰이 5만 → 7만 → 8만이면 시도별 비용 5만·2만·1만도 복원할 수 있어야 한다. 토큰을 읽지 못하면 0으로 대체하지 않는다.
- 수정은 최대 두 번이다. 토큰 사용량이나 측정 누락으로 추가 수정을 중단하지 않는다. 미달과 중단 결과에도 모든 사용량과 점수를 남긴다. [변경 요청](../FEEDBACK/REQ01/remove-token-stop.md)을 참조한다.
- 전체 품질 판정의 목표는 필수 기능 100%와 종합 점수 90점 이상이다. 이 종합 점수의 평가 기준·가중치·증거가 확정되기 전에는 객관 검사 통과율을 전체 합격으로 사용하지 않는다.
- 자동 품질 판정은 [품질 평가 계약](../SPEC/REQ01/quality-evaluation.md)의 기능 40·접근성 15·정적 분석 20·AI 코드 품질 25점으로 계산한다. 빌드·타입·린트와 필수 기능은 합격의 필수 조건이다. 시각 유사도는 별도 평가로 남긴다. [변경 요청](../FEEDBACK/REQ01/code-quality-evaluation.md)을 참조한다.
- 화면의 시각적 품질은 사용자가 직접 판단한다. 외부 기능 평가가 놓칠 수 있는 조작 조합과 예외 상태는 [기능 누락 점검표](../../evaluators/functional-review.md)로 결과마다 별도 확인한다. 이 점검 결과를 기존 자동 점수에 소급 반영하지 않는다. [변경 기록](../FEEDBACK/REQ01/manual-visual-functional-review.md)을 참조한다.
- 같은 비교군 기준·고정 AI 평가 모델·격리된 읽기 전용 평가 복사본을 사용한다. 평가기 사용량은 구현 시도 사용량과 별도로 기록하고 저장된 실행 결과를 재평가할 수 있어야 한다.
- Runner의 FE-01 실제 실행은 별도 활성화 옵션 없이 모든 시도가 끝난 뒤 전체 품질 평가를 항상 실행한다. `--judge-home`을 생략하면 첫 번째 선택 환경의 Codex 인증 홈을 평가 인증 원본으로 사용하고, 평가기는 이를 격리된 임시 홈에 복사한다.
- Promptfoo 비교에는 비교 가능한 객관 검사와 동일한 실행 조건을 사용한다. 평가기 자체에 LLM 호출을 추가하면 그 토큰은 구현 시도 토큰과 별도로 집계한다.
- 실제 전체 벤치마크 실행은 별도 승인 범위에서 수행한다.
- 실제 벤치마크 전 제한 검증은 객관 진단 점수의 낮은 중단 기준(기본 50점)을 사용할 수 있다. 이 기준에 도달해도 전체 품질 합격으로 기록하지 않는다. [요청 배경](../FEEDBACK/REQ01/low-cost-validation.md)을 참조한다.

## 수용 기준

- [x] 같은 초기 입력의 독립 반복과 같은 세션의 피드백 수정을 구분한 실행 기록 형식이 있다. `runner/execution/trial.mjs`의 가상 실행 테스트에서 확인했다.
- [x] 최초·첫 수정·둘째 수정 각각의 점수와 점수 변화, 입력·출력·캐시 토큰 증분 및 누적값을 저장한다. `runner/runner.test.mjs`에서 5만·2만·1만 → 8만 누적 사례를 확인했다.
- [x] 평가 항목이 미완성이면 전체 품질을 합격으로 판정하지 않는다. `evaluators/quality.test.mjs`에서 객관 점수와 미완료 상태를 확인했다.
- [x] 수정 기회를 최대 두 번으로 제한하고 토큰 사용량이 커도 피드백 수정을 계속한다. `runner/runner.test.mjs`의 큰 사용량 사례로 확인했다.
- [x] 제한 검증의 낮은 진단 점수에 도달하면 조기에 멈추고 전체 합격과 구분한다. `runner/runner.test.mjs`의 가상 실행에서 확인했다.
- [x] 최초 Codex 호출과 명시적 세션 ID를 사용한 수정 호출의 명령 구성을 구분한다. `runner/runner.test.mjs`에서 API 호출 없이 확인했다.
- [x] 작은 ZIP 과제 FE-02의 실제 최초 실행·객관 평가·시도별 사용량 기록을 확인했다. [검증 기록](../REVIEW/REQ01/Phase01.md)을 참조한다.
- [x] FE-02를 Baseline·codex-workspace에서 같은 입력·모델·추론 설정으로 각 1회 실행해 객관·정적 검사와 Promptfoo 비교를 확인했다. [Phase02 검증 기록](../REVIEW/REQ01/Phase02.md)을 참조한다.
- [ ] 현재 FE-01 실제 Codex 세션에서 resume·평가·수정 연결을 확인한다. 과거 FAQ 제한 실행은 첫 시도가 진단 목표를 넘어서 수정 호출이 발생하지 않았다.
- [x] 코드 품질을 포함한 자동 품질 루브릭과 가중치·필수 합격 조건을 확정하고, 저장된 FE-02 결과의 객관·정적 재평가 및 모의 AI 채점을 검증했다. 시각 유사도 평가는 별도로 남는다.
- [x] FE-02 두 저장 결과의 실제 `agent-rubric` 평가에서 코드 근거·평가기 토큰·자동 품질 판정을 확인했다. [Phase02 검증 기록](../REVIEW/REQ01/Phase02.md)을 참조한다.
- [ ] 실제 Promptfoo `agent-rubric` 호출에서 근거·토큰 수집과 현재 FE-01의 완전한 자동 품질 판정을 검증한다.
- [x] FE-01 Runner가 `--evaluate-quality` 없이 전체 품질 평가와 Markdown 보고서를 생성하도록 하고 `runner/runner.test.mjs`와 dry-run으로 기본 활성화를 검증했다.
- [ ] 동일 품질에 도달한 비교군의 누적 비용과 미달 비교군의 비용을 함께 보고한다. 전체 품질 판정 전에는 확정할 수 없다.
