# FE-01 run-02 토큰 사용량 분석 및 개선 방안

## 1. 토큰 사용량 차이 분석

### 사용자 질문

> 그리고 토큰 소모가 많이 차이났어. 어느 부분에서 codex-workspace의 토큰이 많이 소모됐는지 체크해줘.

### 에이전트 답변

FE-01 run-02에서 codex-workspace는 baseline보다 **510,768토큰을 더 사용**했고, 그 차이의 **97.6%는 캐시 입력**이었습니다.

실행 로그에서 가장 눈에 띄는 차이는 구현 전에 더 많은 스킬 문서를 읽었고, 구현 후에도 국기 이미지와 UI를 수정·재검증하면서 그동안 쌓인 문맥을 더 여러 번 사용했다는 점입니다.

#### 1.1 토큰 사용량 비교

| 구현 토큰   |    baseline | codex-workspace |         차이 |
| ----------- | ----------: | --------------: | -----------: |
| 캐시 입력   |     401,536 |         900,224 |     +498,688 |
| 비캐시 입력 |      37,985 |          48,141 |      +10,156 |
| 출력        |       6,669 |           8,593 |       +1,924 |
| **합계**    | **446,190** |     **956,958** | **+510,768** |

- 캐시 포함 전체 토큰: **2.14배**
- 비캐시 입력 + 출력: 44,654 → 56,734토큰 (**1.27배**)
- 비교 대상은 구현 시도의 토큰 사용량이며, 외부 AI 품질평가는 별도입니다.

**원본 로그**

- baseline: `~/.local/state/skill-benchmark/results/FE-01/run-02/attempts/baseline/attempt-01/events.jsonl`
- codex-workspace: `~/.local/state/skill-benchmark/results/FE-01/run-02/attempts/codex-workspace/attempt-01/events.jsonl`

#### 1.2 원인 분석: 구현 전 스킬 문서 탐색

baseline은 `Sites/SKILL.md`를 읽은 명령에서 13,739자를 반환했습니다.

반면 codex-workspace는 다음 순서로 문서를 탐색했습니다.

1. skill-router
2. 스킬 맵과 3개 스킬
3. 참조 인덱스
4. 세부 문서

이 과정에서 실행된 5개 명령의 출력은 총 59,615자였으며, 일부 프로젝트 조회 및 설치 출력도 포함되어 있습니다.

특히 레이아웃·타이포그래피·아이콘·Tailwind·코드 스타일 등을 함께 읽은 명령 하나에서만 25,034자가 반환되었습니다.

반면 기대했던 `workspace-unit-doc-manager`나 라우팅 `architecture.md`를 읽는 데 이만큼 사용한 것은 아닙니다.

**관련 로그**

- baseline 스킬 조회: `events.jsonl:5`
- codex-workspace 세부 문서 조회: `events.jsonl:18`

#### 1.3 원인 분석: 구현 후 국기 이미지 및 레이아웃 재검증

두 환경 모두 브라우저 검증을 시도했습니다.

codex-workspace는 원격 국기 이미지 로딩 문제를 발견한 이후 다음 작업을 추가로 수행했습니다.

1. SVG 국기 이미지 250개를 로컬에 저장
2. 브라우저에서 250개 이미지의 디코딩 여부 검사
3. 생성된 CSS 확인
4. 상세 화면의 간격 수정
5. 수정 후 재빌드 및 검증

전체 완료 셸 명령 수는 다음과 같습니다.

| 환경            | 완료 셸 명령 |
| --------------- | -----------: |
| baseline        |         12개 |
| codex-workspace |         19개 |

SVG 이미지는 파일로 저장되었고 다운로드 명령의 출력은 186자에 불과했습니다.

따라서 이 구간의 토큰 차이를 설명하는 주요 요인은 이미지 파일 크기보다 **추가 수정과 검증 과정에서 기존 문맥을 반복적으로 재사용한 횟수**로 판단됩니다.

**관련 로그**

- 국기 다운로드: `events.jsonl:37`
- 브라우저 재검증: `events.jsonl:41`
- 마지막 수정 및 빌드: `events.jsonl:45`

위 로그 위치는 모두 codex-workspace의 `attempt-01/events.jsonl` 기준입니다.

#### 1.4 분석 결론

확정할 수 있는 사실은 추가 토큰의 거의 전부가 캐시 입력이었다는 점입니다.

다만 저장 로그는 구현 턴 전체의 토큰 사용량만 제공하므로, 추가 캐시 입력 498,688토큰 중 정확히 몇 개가 스킬 탐색이나 브라우저 검증에서 발생했는지는 분리할 수 없습니다.

현재 가장 근거 있는 해석은 다음과 같습니다.

- **초반:** 넓은 범위의 참조 문서 탐색으로 문맥이 증가했습니다.
- **후반:** 추가 수정 및 검증 과정에서 누적된 문맥이 반복적으로 입력에 포함되었습니다.

따라서 단순히 문서 탐색량뿐 아니라, 누적된 문맥을 재사용하는 작업 횟수도 토큰 증가에 영향을 준 것으로 판단됩니다.

## 2. 토큰 사용량 개선 방안

### 사용자 질문

> 이는 어떻게 해결해야 할까?

### 에이전트 답변

FE-01 결과를 보면 가장 먼저 개선할 부분은 **codex-workspace의 참조 문서 선택 규칙**입니다.

이번 실행에서는 구현 전에 스킬 관련 명령 5개에서 약 6만 자를 읽었지만, 정작 기대했던 문서 계획과 라우팅 구조를 검토한 흔적은 없었습니다.

따라서 불필요한 토큰 사용량을 줄이면서 스킬 준수도도 높일 여지가 있습니다.

#### 2.1 개선 우선순위

| 우선순위 | 개선 대상                              | 개선 방향                                                    |
| -------- | -------------------------------------- | ------------------------------------------------------------ |
| 1        | skill-router 및 개별 스킬              | 구현 전 필요한 설계 결정을 기준으로 참조 문서를 선택         |
| 2        | react-ui-style, code-style 참조 인덱스 | 중첩된 README 탐색을 줄이고 SKILL.md에서 직접 참조 조건 안내 |
| 3        | 구현 후 검증                           | 검증 항목을 묶어 실행하고 실패한 항목만 재검증               |

#### 2.2 개선안 1: 참조 문서 선택 기준 변경

현재는 구현 전에 광범위한 스타일 및 코드 관련 문서를 읽는 경향이 있습니다.

이를 작업 단계별로 필요한 문서만 선택하는 방식으로 변경합니다.

FE-01을 기준으로 다음과 같이 적용할 수 있습니다.

**구현 전**

- 문서 계획 확인
- 목록 및 상세 경로 설계
- 필요한 아키텍처 결정

**구현 중**

- 레이아웃 관련 작업 시 레이아웃 문서 참조
- 타이포그래피 작업 시 타이포그래피 문서 참조
- 아이콘 작업 시 아이콘 문서 참조
- Tailwind 및 코드 스타일 문서는 해당 규칙이 필요한 시점에 참조

이를 통해 실제 작업과 무관한 문서의 선행 로딩을 줄입니다.

#### 2.3 개선안 2: 참조 인덱스 탐색 경로 단축

현재 문서 탐색은 다음과 같은 다단계 구조를 거칠 수 있습니다.

`SKILL.md → 분야별 README → 하위 README → 세부 문서`

이를 개선하여 `SKILL.md`에서 자주 사용하는 세부 문서의 경로와 읽어야 하는 조건을 직접 안내하도록 합니다.

에이전트가 여러 인덱스를 순차적으로 열지 않고 필요한 문서를 선택할 수 있도록 하는 것이 목적입니다.

#### 2.4 개선안 3: 구현 후 검증 효율화

브라우저 검증 자체는 유지해야 합니다.

실제로 이번 실행에서는 브라우저 검증을 통해 국기 이미지 로딩 문제를 발견했습니다.

다만 관련 수정을 완료한 후 한 번의 빌드와 브라우저 실행에서 다음 항목을 함께 검사하도록 개선합니다.

- 이미지 로딩
- 키보드 탐색
- 상세 화면 이동
- 이전 화면 복귀 및 상태 유지

검증에 실패한 항목만 수정 후 다시 검사하는 방식입니다.

**주의사항**

셸 명령 수에 일괄 상한을 두는 방식은 권장하지 않습니다.

긴 문서 여러 개를 `cat` 명령 한 번으로 읽는 행동은 제한하지 못하면서, 실제 결함을 발견하는 데 필요한 브라우저 검증만 줄일 수 있기 때문입니다.

## 3. 개선 효과 검증 계획

### 3.1 측정 지표

토큰 사용량을 비교할 때는 캐시 포함 전체 토큰과 비캐시 입력·출력을 함께 확인해야 합니다.

이번 실행의 기준값은 다음과 같습니다.

| 지표                | codex-workspace / baseline |
| ------------------- | -------------------------: |
| 캐시 포함 전체 토큰 |                     2.14배 |
| 비캐시 입력 + 출력  |                     1.27배 |

토큰 사용량만 감소했다고 해서 반드시 개선된 것은 아닙니다. 필수 작업이나 검증을 생략한 결과일 가능성도 고려해야 합니다.

### 3.2 권장 적용 순서

1. 최신 버전으로 동일한 FE-01 벤치마크를 먼저 실행합니다.
2. 새 실행 로그를 기준으로 참조 문서 선택 과정을 분석합니다.
3. 분석 결과에 따라 참조 규칙을 수정합니다.
4. 동일한 입력과 모델을 사용하여 다시 비교합니다.

기존 run-02는 구버전이며, 최신본에는 이미 문서 관리 스킬의 선택 조건이 보강되어 있습니다.

따라서 기존 결과만으로 추가 변경을 진행하기보다 최신 실행 결과를 먼저 확보하는 것이 좋습니다.

### 3.3 비교 시 확인할 항목

| 항목                      | 확인 목적                          |
| ------------------------- | ---------------------------------- |
| 첫 코드 수정 전 참조 문서 | 불필요한 문서 탐색 여부            |
| 산출물의 구조             | 기대한 설계 및 문서 구조 반영 여부 |
| 필수 기능 통과 수         | 기능 품질 유지 여부                |
| 비캐시 입력 및 출력 토큰  | 새로운 입력 및 생성량 변화         |
| 캐시 포함 전체 토큰       | 누적 문맥 재사용 비용 변화         |

### 최종 결론

이번 FE-01 run-02의 토큰 사용량 증가는 **초기 참조 문서 탐색 범위와 후속 수정·검증 과정에서의 누적 문맥 재사용**이 주요 원인으로 추정됩니다.

우선적으로 참조 문서 선택 규칙을 개선하되, 브라우저 검증처럼 실제 결함을 발견하는 작업은 유지해야 합니다.

최신 버전의 동일 벤치마크를 다시 실행한 후 토큰 사용량과 기능 품질을 함께 비교하는 것이 적절합니다.
